# Contributing to the OpenPiste Protocol

Thank you for your interest in contributing. This specification is developed openly and all feedback is welcome — whether you are a developer, an armourer, a referee, a competition organiser, or simply someone who uses fencing electronics.

---

## Ways to contribute

### Report an error or inconsistency

If you find something in the spec that is wrong, ambiguous, or contradicts how real fencing equipment works — open an issue. Please describe:

- Which document and section the issue is in
- What the current text says
- What you believe it should say, and why

### Ask a question

If something in the spec is unclear, open an issue with your question. Unclear spec text is itself a bug — if you had to ask, the text probably needs improving.

### Propose a change

If you have a specific change to propose, open an issue first to discuss it before submitting a pull request. This avoids wasted effort if the change turns out not to be the right direction.

For small corrections (typos, formatting, broken links), a pull request without a prior issue is fine.

### Share implementation experience

If you have implemented part of this protocol — or tried to — your experience is valuable. What was unclear? What was missing? What worked well? Open an issue or start a discussion.

### Domain knowledge

You do not need to be a developer to contribute. Knowledge from:

- **Armourers** — how scoring apparatus actually behaves in practice
- **Referees and technical officials** — what information needs to be visible and when
- **Competition organisers** — what the management software side needs
- **Federation officials** — rule changes that affect protocol requirements

...is equally important as technical input. Open an issue or discussion and describe your perspective.

---

## What we are not looking for

- Changes that break backward compatibility without a very strong reason
- Features that cannot be implemented on resource-constrained hardware (ESP32)
- Additions that duplicate information already carried in another message type

---

## Pull request guidelines

- One change per pull request
- Update the relevant section only — do not reformat unrelated sections
- If your change affects multiple documents, update all of them
- Add a brief description of what changed and why in the pull request body

---

## Code of conduct

This project follows the standard open source norms: be respectful, assume good faith, and focus on the technical merits of proposals. Discussions about fencing rules or federation politics belong elsewhere.

---

## Questions?

Open an issue or start a discussion. There are no stupid questions about protocol specifications.
